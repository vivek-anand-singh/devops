# Introduction to CI/CD — Basics

## What Is CI/CD?

**CI/CD** stands for **Continuous Integration** and **Continuous Delivery** (or **Continuous Deployment**). It is a set of practices and tools that help teams:

- **Build**, **test**, and **release** software more often and more reliably  
- **Automate** steps that used to be manual  
- **Catch bugs early** and **deploy** with less risk  

---

## CI — Continuous Integration

**Continuous Integration** means developers **merge their code** into a shared branch (e.g. `main`) frequently, and each change is **automatically built and tested**.

### Key ideas

- **Small, frequent commits** instead of big merges  
- **Automated build** on every push (or pull request)  
- **Automated tests** (unit, integration) run on every change  
- **Fast feedback** — if something breaks, you know quickly  

### Why it helps

- Reduces **merge conflicts** and **integration bugs**  
- Keeps the codebase in a **working state**  
- Makes it easier to **find and fix** issues early  

---

## CD — Continuous Delivery vs Continuous Deployment

| Term | Meaning |
|------|--------|
| **Continuous Delivery (CD)** | Code is **always in a deployable state**. You can release to production **any time** with one click or command. Release to production is **manual**. |
| **Continuous Deployment** | Every change that passes the pipeline is **automatically** deployed to production. No manual approval for release. |

In practice, “CI/CD” often covers both: **integrate continuously** and **deliver/deploy** in an automated way.

---

## The Pipeline

A **CI/CD pipeline** is the automated sequence of steps that run when code changes (e.g. on git push or PR).

### Typical stages

1. **Source** — Code is committed and pushed (e.g. Git).  
2. **Build** — Compile code, install dependencies, create artifacts (e.g. JAR, Docker image).  
3. **Test** — Run unit tests, integration tests, linting, security scans.  
4. **Deploy (staging)** — Deploy to a test/staging environment.  
5. **Deploy (production)** — Deploy to production (manual in CD; automatic in Continuous Deployment).  

```
  Code Push
       ↓
  [ Build ]
       ↓
  [ Test ]
       ↓
  [ Deploy Staging ]  →  [ Deploy Production ]
```

---

## Key Concepts

| Concept | Description |
|--------|-------------|
| **Pipeline** | End-to-end automation: build → test → deploy. |
| **Stage / Job** | A step in the pipeline (e.g. “build”, “test”, “deploy”). |
| **Artifact** | Output of a stage (e.g. binary, Docker image, zip) used in later stages. |
| **Trigger** | What starts the pipeline (e.g. push to `main`, merge, tag, schedule). |
| **Environment** | Where the app runs (e.g. dev, staging, production). |

---

## Benefits of CI/CD

- **Faster releases** — Ship features and fixes quickly.  
- **Fewer bugs** — Automated tests catch issues before production.  
- **Consistent process** — Same steps every time; less human error.  
- **Easier rollbacks** — Known good builds and clear deployment history.  
- **Better collaboration** — Shared pipeline and visibility for the team.

## Common CI/CD Tools

| Tool | Type | Notes |
|------|------|--------|
| **Jenkins** | Self-hosted, open source | Plugins for almost everything; very flexible. |
| **GitHub Actions** | Cloud, integrated with GitHub | Workflows in YAML; good for GitHub repos. |
| **GitLab CI/CD** | Built into GitLab | Pipelines defined in `.gitlab-ci.yml`. |
| **Azure DevOps** | Microsoft cloud | Pipelines, boards, repos in one place. |
| **CircleCI** | Cloud | Simple config; good for open source and startups. |
| **Tekton / Argo CD** | Kubernetes-native | Tekton for pipelines; Argo CD for GitOps deployments. |

## A Simple Mental Model

1. **Developers** push code to a repo (e.g. Git).  
2. **CI** runs on every push: **build** + **test**.  
3. If tests pass, the build is **ready to deploy** (artifact or image).  
4. **CD** takes that artifact and **deploys** to staging, then (when approved or automatic) to production.  
5. **Monitoring** and **logs** help you see if production is healthy; if not, you **roll back** or fix forward.  

---

## Best Practices (Summary)

- **Automate** build, test, and deploy; avoid manual steps.  
- **Run tests early** — fail fast if something is broken.  
- **Keep pipelines fast** — optimize so developers get feedback quickly.  
- **Use version control** for pipeline config (e.g. Jenkinsfile, `.yml` in repo).  
- **Treat pipeline as code** — review and test changes to the pipeline like application code.  
- **Use environments** — dev → staging → production with clear promotion rules.

## Quick Definitions (Cheat Sheet)

| Term | One-liner |
|------|-----------|
| **CI** | Automatically build and test on every code change. |
| **CD (Delivery)** | Always deployable; release to production is manual. |
| **CD (Deployment)** | Automatically deploy to production when pipeline passes. |
| **Pipeline** | Automated flow: build → test → deploy. |
| **Artifact** | Build output (e.g. binary, image) used for deployment. |
| **Trigger** | Event that starts the pipeline (e.g. git push). |
